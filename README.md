# Agentic Article Summarizer

- Агент получает JSON-файла cо статьями, последовательно суммаризует их и сохраняет результаты в отдельный JSON-файл;
- В качестве оркестратора используется `qwen/qwen3.6-27b` через Groq API, в качестве суммаризатора - `mistral-small-latest` через Mistral API;
- Обработка статей идёт без Python-цикла, последовательностью управляет LLM.

## Architecture

- LangChain `create_agent` - создание и запуск агента
- `qwen/qwen3.6-27b` через Groq - оркестрация и выбор tool
- `mistral-small-latest` - суммаризация статей
- MCP server - файловые операции `read_json` и `save_result`
- `SummarizationMiddleware` - сжатие истории длинной сессии

```text
Agent
├── MCP: read_json
├── local: summarize_article
└── MCP: save_result
```

## How it works

```text
read_json()
↓
получить список id/title
↓
read_json(article_id=...)
↓
summarize_article
↓
save_result
↓
следующая статья
```
Агент получает список доступных id, после чего самостоятельно определяет последовательность вызовов инструментов для обработки каждой статьи: получает полный текст, вызывает суммаризацию и сохраняет результат. После успешного сохранения агент переходит к следующей статье. Цикл обработки статей на уровне Python отсутствует.

## MCP

- в MCP вынесен слой файлового I/O - `read_json` и `save_result`
- `read_json` отвечает за чтение входных данных, `save_result` — за сохранение результатов. Это позволяет отделить файловые операции от LLM-логики суммаризации.
- mcp_server.py публикует инструменты, `main.py`. Полученные MCP tools затем передаются в create_agent() вместе с локальным summarize_article

## Long Agent Session

- При последовательной обработки статей история сообщение агента увеличивалось. Это приводило к росту контекста и перерасходу токенов
- Для сжатия истории использовался SummarizationMiddleware, запускающий сжатие при достижении 4000 токенов, при этом сохраняются последние 8 сообщений
- Используется `summary prompt` для запоминания обработанных и необработанных id, текущий id, последовательность действий для каждой статьи и условие завершения работы агента

## Summary Quality

- Первоначально summary были слишком длинными и мало отличались от исходных текстов
- Первоначальный prompt требовал сохранять ключевые числа, сроки и ограничения, из-за чего модель сохраняла слишком много второстепенных деталей.
- Помимо информационного сжатия, summary было ограничено 2-3 предложениями и ограничением генерации череp `max_tokens`
- В результате summaries стали заметно короче, сохраняя основную мысль статьи.
